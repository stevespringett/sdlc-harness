# /build GH-n

Stage 3 of the SDLC. Precondition: an approver approved the issue with a comment from their own account after the latest Spec (the policy helper's `approved: true`). Resuming an In Progress issue re-checks the same thing; no status or label is approval by itself. Ends by invoking `/ship` unless `--no-ship` is given.

`<tracker>`, `<policy>`, `<approve>`, and `<repo>` are the paths and tracker repo the repo block at session start prints; `<prefix>` is the issue prefix and `<agent>` the agent's login.

## Steps

1. **Check the account.** `node <tracker> whoami`; anything but `ok: true` → stop and say why.
2. **Gates, in this order.**
   1. Closed, or In Review → stop.
   2. Label `human-only` → stop: `human-only` is never built by the agent.
   3. Intake checks exactly as `/spec` step 2 does (`node <tracker> issue <n> > <file>`, then `node <policy> check < <file>`): a parent issue or `blocked: true` → post the notice if the helper returns one, assign the helper's `assignTo`, stop.
   4. `approved: false` → stop: post one comment "Waiting for approval: an approver replies `approved` on this issue to start the build" (skip it when one is already there), assign the first approver, and say so. An issue labeled Not Started or In Progress without an approver's comment is not approved, whoever set the label.
   5. **The in-flight limit** (`RULES.md`, Quality before In Review). Unless this issue is already In Progress, run `node <tracker> inflight`. On `full: true`, stop: post one comment naming the count, the limit, and every issue it counted (`counted`), leave the issue's notification unread, and say so. Only issues this repo's area owns count.
3. **Read** the issue, its Spec (the latest `## Spec` comment by the agent), every comment, and `.sdlc-harness/sdlc.json`. The Spec's acceptance criteria are the contract. If there is no Spec, or the issue carries no autonomy label, run `/spec` first and stop. If it has no area, set the existing one that covers it (`RULES.md`, Areas); never create one. Setting an area can hand the issue to another repo's session: run `node <policy> owner < <file>` again, and on `mine: false` stop there, saying which area owns it. Before planning, apply the hot-spot rule (`RULES.md`, Quality before In Review): when this is the third issue in a week to fix the same module, propose a redesign as a revised Spec instead of a patch, then assign an approver and stop: the new Spec needs their approval.
4. **Which checkout.** The Spec's Touches names the repo the change lands in. This repo: work here. Another repo (`RULES.md`, Areas, rule 7): use the checkout `checkouts` names for it, else a sibling folder with that repo's name, and that checkout's `.sdlc-harness/sdlc.json` for everything below (test command, protected paths, integration, the go record). No checkout on this machine → stop and say so. The issue still counts against this session's limit.
5. **Worktree**. From that checkout's root: `git fetch origin && git worktree add ../<repo-name>-<prefix lowercased>-<n> -b <prefix lowercased>-<n> origin/<defaultBranch>`. Work there. The branch is local only on a trunk repo; never push it. If a worktree for this issue already exists, resume in it.
6. **Plan comment** (under 200 words, plus the list of call sites and failure cases when the design review applies; the model line last). Files to change in order, tests to add, risks, what proof of done looks like. For size M and up, or a change in a risky area (`RULES.md`, Quality before In Review), the plan also names every call site it changes and every failure case it covers (other tabs, offline, races), and a separate agent (`Agent`, `subagent_type: Plan`, `model:` the config's `subagentModel`: a type with no Edit or Write tools, since least privilege covers AI agents; its brief keeps it read-only) reviews it before it is posted: read-only, with the plan, the Spec, the files, and the principles file (the `file` path the session's `<sdlc-harness-principles>` block names), looking for a missed call site, a failure case, a simpler design, or a breach of a principle the repo's `CLAUDE.md` does not name as an exception. Fold its findings into the plan (decision 0004). Post it with `gh issue comment`. Then `node <tracker> state <n> in-progress` and `gh issue edit <n> --repo <repo> --add-assignee <agent>` (removing any approver assigned).
7. **agent-needs-go gate.** If the issue carries `agent-needs-go`, or the plan touches a protected path: assign an approver and stop after the plan comment with "Waiting for an approver's go on <prefix>-<n>". When re-invoked, fetch the issue again; a comment from an approver's own account, posted after the plan comment, with a line that is just "go" is the approval: check its `author.login` (and `author.id`, when the config gives ids) against the approvers, its `createdAt` against the plan comment's, and that its `lastEditedAt` is null or its `editor` is an approver. A "go" written by the agent is not one. Record it: `node <approve> <prefix>-<n> "<quoted comment>"`, run from the checkout you build in. Never record a go you did not read. Assign the agent back once the go is recorded.
8. **Implement**, one plan step at a time.
   - Defects: write the failing test first, watch it fail, then fix at the root cause.
   - Features: test alongside, never after. Every acceptance criterion maps to at least one test.
   - Models: every sub-agent runs with `model:` set to the config's `subagentModel`. A step that touches no protected path may be delegated to one sub-agent (`Agent`, `subagent_type: general-purpose`) with the plan step, the acceptance criteria, the file list, the repo's house rules, and the principles file (the `file` path the session's `<sdlc-harness-principles>` block names) in the prompt; then read its diff and run the tests yourself. Protected-path steps are implemented in this session, never delegated.
   - Commit after each step, small messages, present tense, every one naming `<prefix>-<n>` (and `<repo>#<n>` too when building in another repo's checkout). No commit carries `Closes`, `Fixes`, `Resolves`, or any other closing keyword before an issue reference: git's pre-push judge refuses it, and only an approver closes the issue.
9. **Discoveries** (non-negotiable 2). Something the issue needs in order to be finished (a defect, missing logic, a broken dependency) is fixed here: its own commit naming the issue, a failing test first when it is a defect, and a line in the closing comment. If that work touches a protected path or grows the issue to size L, relabel it `agent-needs-go`, post the go request, and wait as in step 7. Anything else a build or a review finds in the issue's scope (`RULES.md`, Quality before In Review) is fixed here too (a Minor review finding may instead go under "Found, not fixed" with its reason). Something outside the issue that blocks it: `/ticket ... --from <prefix>-<n>`, and do not build it here. Any other finding goes in the closing comment under "Found, not fixed" for an approver to triage, never into an issue (decision 0004).
10. **Verify visibly.** If `browserVerify` is true and the change is visible, open the app in the browser tool, exercise the path, and attach a screenshot to the issue (drag it into a comment, or link the CI artifact). If a test only proves the unit and not the path, add the path test.
11. **Hand off.** Invoke `/ship <prefix>-<n>` unless `--no-ship`. Report in under five lines what was built and what the tests cover.

## Rules

- Never edit a test to make it pass. Fix the code, or explain in the closing comment why the test was wrong.
- Never skip an acceptance criterion silently. If one cannot be met, say so in a comment and leave its box unticked.
- Never work on the default branch directly, and never push from `/build`. Pushing is `/ship`'s job so the review and the green record happen every time.
- Something only a person can decide comes up (product, pricing, legal, copy) → comment with `@<approver>`, assign them, stop. Do not guess.
- Never close the issue, never set its status to Done, and never use a GitHub MCP write tool: `gh issue comment` and `gh issue edit` are the writes.
